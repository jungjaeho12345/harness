# Step 4: read-service

기사 **읽기 서비스**를 만든다. HTTP 비의존이며, 응답으로 나가는 행을 만드는 **유일한 지점**이 여기다.

두 갈래를 소유한다: (a) 기사 읽기 — 단건 조회·목록 조회·검색 (b) 이력 읽기 — 이력 목록(표시 파생 + 송고 필터)·단건 스냅샷. 둘 다 읽기 전용이며 DB를 바꾸지 않는다.

## 읽어야 할 파일

- `server/index.js` 793~850행 — 라우트가 서비스에 위임하는 얇은 형태(다음 step들이 이식할 대상 — 지금은 참조만)

## 배경 (동결된 계약 사실)

- **단건 조회**는 `{article, contents}`를 돌려주고 둘 다 없으면 '없음'이다(HTTP 계층이 404로 바꾼다). `contents`는 **투영 후 27키**, `article`은 5키.
- **목록·검색**은 배열을 돌려주며 **총수·페이징 필드가 없다**(그 '없음'이 계약이다).
- **검색 행은 `Article` 행**이라 목록 행과 shape이 다르다(본문 `markupVersion`이 실려 나간다). 같은 투영을 통과시키되 결과적으로 제거되는 키는 없다.
- **이력 목록**: 이력이 없거나 **기사가 존재하지 않아도 200 빈 배열**이다(404가 아니다). 표시 파생은 **송고 필터 이전에** 전체 이력 기준으로 계산한다(승계 규칙이 잘린 행에 의존한다).
- **송고 필터 판정(라우트 소유지만 서비스가 결과를 강제)**: `sendOnly` 파라미터가 존재하고 값이 `'0'`도 `'false'`도 아니면 참, 또는 `type === 'send'`면 참. 빈 문자열·`'no'`도 **참**이다. 필터가 걸리면 `eventType === 'status'`이면서 `action === 'send'`인 행만 남는다.
- **v1 본문 예외**: 이력이 1건 이상이고 스냅샷이 0건일 때만 현재 본문을 v1 본문으로 넘긴다. 그 외에는 **조회하지 않는다**(불필요한 blob 읽기 금지).
- **표시 제목 입력 조회는 가드 호출**이다: 실패해도 이력보기가 죽지 않고 제목만 빈다(2차 폴백 금지 — 장애 시 본문 전량 읽기가 되살아나는 경로를 만들지 않는다).
- **단건 스냅샷**은 `articleId` 스코프로만 조회하고 없으면 `not-found`. 스냅샷이 없는 전이 행도 **200이고 본문만 `null`**이다.

## 작업

### A. 기사 읽기 서비스

- 단건 조회: 리포지토리 결과에 **투영을 적용한 `contents`**로 바꿔 돌려준다. 한쪽 테이블 행이 없으면 그 키를 **싣지 않는다**(decisions (20) — HTTP 계층이 그대로 직렬화한다).
- 목록 조회: 필터 맵(원문 `키 → 값 배열`)을 리포지토리에 그대로 넘기고 결과를 **행마다 투영**한다.
- 검색: 질의 문자열(없으면 빈 문자열)로 리포지토리 검색 → 같은 투영을 통과시킨다.
- **투영을 우회하는 읽기 경로를 만들지 마라** — 내부 판정용 원본이 필요한 곳은 리포지토리를 직접 부른다(잠금·전이 서비스가 그렇게 한다).

### B. 이력 읽기 서비스

- 이력 목록: 리포지토리 목록 조회 → (조건부) 표시 제목 입력 조회 → (조건부) v1 본문 조회 → step1의 표시 파생 → **필요하면 송고 필터**. 순서를 바꾸지 마라.
- 표시 제목 입력 조회와 v1 본문 조회는 **각각 try/catch로 격리**한다(실패해도 목록은 돌려준다 — 정본과 동형).
- 단건 스냅샷: 리포지토리 결과가 없으면 `not-found` 사유, 있으면 그대로 항목을 돌려준다(투영 대상 아님 — 잠금 컬럼이 없는 테이블이다).

### C. 필터 입력 계약 고정

- 서비스가 받는 필터는 **화이트리스트 13키로 이미 걸러진 원문 값 배열 맵**이다. 화이트리스트 자체(어떤 키를 통과시킬지)는 HTTP 계층이 소유한다(Node의 `pickFilters`가 라우트 옆에 있는 것과 동형).
- 서비스는 값 배열을 **재해석하지 않는다**(콤마 분해·형변환 금지 — decisions (10)).

### D. 테스트 (먼저 쓴다 — `@TempDir` DB + 실제 리포지토리, HTTP 없음)

1. 단건 조회: 잠금이 걸린 기사에서 `contents`가 **27키**이고 `lockerSessionId`·`lockerClientId` 키가 **없으며** `lockYN`·`lockerUserId`·`lockedAt`은 있다.
2. 단건 조회: 없는 id → '없음'. 한쪽 테이블 행만 있는 경우 → 그 키만 실린다.
3. 목록: 투영이 **모든 행에** 적용된다(잠긴 행 2건 이상으로 실증). 총수·페이징 키가 없다.
4. 검색: 결과 행이 `Article` 5키다.
5. 이력 목록: 이력 0건 → 빈 배열 · 존재하지 않는 기사 → 빈 배열(예외 아님).
6. 이력 목록: 편집 1 + 전이 1 시나리오에서 12키·`version`·`status`·`title`이 계약과 같다.
7. 송고 필터: 걸리면 `status`/`send` 행만 남고, **표시 파생은 필터 전 전체 기준**이라 남은 행의 `version`이 필터 여부와 무관하다.
8. 표시 제목 입력 조회가 예외를 던져도 목록이 돌아온다(제목만 빈다).
9. 스냅샷 0건 + 이력 1건 이상일 때만 v1 본문을 읽는다(스냅샷이 있으면 본문 조회가 **일어나지 않는다** — 호출 횟수 스파이로 실증).
10. 단건 스냅샷: 전이 행도 조회되고 본문이 `null` · 타 기사 스코프는 `not-found`.

## 금지사항

- 읽기 경로에서 DB를 바꾸지 마라(조회 카운터·최근 열람 갱신 등). 이유: 계약이 읽기 전용을 전제하고, 부수효과는 이중 실행 diff를 만든다.
- 투영을 컨트롤러·리포지토리로 옮기거나 복제하지 마라. 이유: 새 라우트에서 반드시 누락된다 — 그것이 이 결함의 원래 원인이다.
- 이력 목록에 본문(blob)을 싣지 마라. 이유: 목록은 경량 계약이고 그 결과는 다른 판정의 입력으로도 쓰인다.
- 표시 제목 조회 실패 시 본문 전량 조회로 2차 폴백하지 마라. 이유: 장애 상황에서 하필 최악 비용이 되살아난다(정본이 명시적으로 금지한 경로).
- 필터 값 배열을 서비스에서 재해석(콤마 분해·트림·형변환)하지 마라. 이유: `?status=RDS,DDH`가 매칭 0건인 것이 계약이다.
- 빈 결과에 404를 돌려주지 마라(목록·검색·이력 전부). 이유: 200 + 빈 배열이 동결된 계약이다.
