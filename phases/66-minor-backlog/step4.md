# Step 4: probe-final-origin

Electron 클라이언트가 서버 주소를 확인할 때 **302 리다이렉트를 조용히 따라가 성공 판정만 하고 최종 주소를 읽지 않아**, 실제 접속되는 곳과 다른 주소가 저장되는 하자(감사 항목 E, low — phase 62/63 이월)를 고친다.

## 배경 (실코드 확인 결과)

- 프로브는 health URL로 요청을 보내고 응답 상태·본문만 판정에 쓴다. Electron의 fetch는 리다이렉트를 기본으로 따라가므로 **302로 다른 호스트에 도착해도 성공**이고, 응답 객체의 최종 URL은 읽지 않는다.
- 두 IPC 핸들러(확인·저장)는 성공 시 **사용자가 입력한 origin**을 그대로 응답하고 저장한다. 저장된 값은 그대로 (i) 설정 파일 (ii) 앱 창이 여는 주소 (iii) 다음 부팅의 secure-origin 스위치 대상 (iv) 재시작 필요 판정 입력이 된다.
- 실패 시나리오(호스트 변경 배치): 프록시가 A → B로 302 → A가 저장됨 → 스위치는 A에만 걸림 → 실제 페이지는 B라 **클립보드 기능이 죽고 재시작해도 낫지 않는다** → A를 폐기하면 접속 불능.
- 설정 화면은 이미 확인 응답의 origin을 그대로 표시하므로, 응답이 최종 주소를 담기만 하면 안내는 자동으로 정렬된다.

## 작업

TDD 순서를 지킨다: **먼저 red 테스트 → 그다음 구현**.

### A. 순수 판정 함수 (`client/lib/serverUrl.js`)

시그니처(형태만 고정, 구현은 재량):

```
resolveFinalOrigin({ requestedOrigin, responseUrl }) -> { origin, changed }
```

규칙(전부 테스트로 잠근다):

- 최종 응답 URL이 없거나 문자열이 아니거나 파싱 불가 → 요청 origin 그대로, `changed`는 거짓.
- 스킴이 http/https가 아니면 → 요청 origin 그대로(fail-safe = 사용자가 친 주소 유지).
- 사용자 이름·비밀번호가 실려 있으면 → 요청 origin 그대로(설정 파일에 자격증명이 남을 자리를 만들지 않는다는 기존 정규화 계약과 동형).
- 그 밖에는 최종 URL의 origin을 돌려주고, 요청 origin과 다르면 `changed`가 참이다.
- 경로·쿼리·해시는 버린다. origin 조립은 반드시 `new URL`로 한다(문자열 자르기 금지 — 파일 상단 CRITICAL).

### B. 결선 (`client/main.js`)

- 프로브 함수가 응답 객체의 **최종 URL**을 읽어 A의 함수에 넘기고, **성공 판정일 때만** 승격된 origin을 채택한다. 실패(도달 불가·상태 이상·기사작성기 서버 아님)면 승격하지 않는다.
- 프로브 반환 계약을 확장한다: **성공/실패와 무관하게 항상 최종 origin을 함께 돌려준다**(성공+리다이렉트면 승격값, 그 밖에는 요청 origin). 그래야 프로브 이후의 모든 소비가 **한 값**만 본다.
- 두 IPC 핸들러(확인·저장)는 프로브 호출 **이후로는 요청 origin 변수를 다시 쓰지 않는다** — 응답의 origin, 저장값, 앱 창이 여는 주소, 재시작 필요 판정 입력이 전부 프로브가 돌려준 값이다(실패 응답의 origin도 마찬가지).
- 진단 이벤트는 기존 이름·기존 필드를 유지하고, 승격 사실을 알 수 있는 **필드를 추가만** 한다. **남기는 값은 승격 결과 origin(경로·쿼리 없는 origin 문자열)과 boolean뿐이다 — 응답 URL 원문을 절대 기록하지 마라.** 근거(실코드): 진단 축약기는 **키 이름에 `url`이 포함될 때만** URL 축약을 적용한다(`client/diag.js` 37행) — `origin`류 키에 응답 URL 원문을 실으면 쿼리(토큰·식별자)가 진단 JSONL에 **평문으로 남는다**. 원 URL을 부득이 남겨야 하면 키 이름에 `url`을 포함시켜 축약기를 경유시켜라.
- 부팅 순서·스위치 적용·창 정책·권한 정책·타이머 없음(ADR-008)은 **한 줄도 바꾸지 마라**.

### C. 테스트 (`test/client-probe-origin.test.js` — 신설, `node:test`)

기존 파일을 고치지 않고 이 phase 전용 파일 하나를 만든다(전례: 클라이언트 기능별 테스트 파일 분리).

1. **순수 함수 단위** — A의 규칙 5종 + 경계: 최종 URL이 요청과 같은 경우, 경로만 다른 경우(origin 동일 → `changed` 거짓), 포트가 다른 경우, 스킴이 http→https로 바뀐 경우, 기본 포트 생략 표기 차이, 자격증명이 실린 최종 URL, 파싱 불가 문자열, `undefined`.
2. **결선 텍스트 잠금 3케이스**(메인 파일은 단위화 불가 — 권한 정책 전례와 동형):
   - (i) 메인 파일이 순수 모듈에서 새 함수를 import한다.
   - (ii) 프로브 함수 본문 안에서 응답 객체의 최종 URL을 읽어 새 함수에 넘긴다.
   - (iii) 두 IPC 핸들러 각각에서, 프로브 호출 줄 **이후**로는 요청 origin 접근 표현식이 등장하지 않는다.
   - **(iii)의 구간 경계를 코드로 못 박아라**(모호한 스캐너는 무관한 코드에 무너진다 — phase 65 전례): 구간은 "해당 핸들러 등록 줄(그 채널 이름이 있는 줄)부터 **다음 핸들러 등록 줄 직전까지**"로 정의하고, 두 구간이 실제로 찾아졌는지(시작 인덱스 ≥ 0, 끝 > 시작)를 먼저 단언한 뒤 그 안에서만 검사한다. 구간을 못 찾으면 "검사 대상 없음"으로 조용히 통과하지 말고 **실패**시켜라.
   - 실패 메시지에 기대 형태와 실제 발견 위치(줄 번호·해당 줄 원문)를 함께 출력해, 되돌린 사람이 이유를 즉시 알게 하라.
   - **needle 선정 주의**: 기존 메인 파일 스캐너(권한 정책 결선)가 쓰는 needle과 겹치지 않는 문자열을 골라라. 그리고 (iii)의 needle은 **테스트 파일 안에서만** 문자열로 쓰고 **메인 파일 주석에는 절대 쓰지 마라** — 스캔은 코드와 주석을 구분하지 않아 설명 주석 하나가 즉시 red를 만든다(phase 65에서 같은 함정이 실증됐다).

## 검증 절차

1. **red 먼저**: C-1의 순수 함수 케이스와 C-2의 텍스트 잠금을 먼저 쓰고, 구현 전에 실패를 확인한다(순수 함수는 미존재로, 텍스트 잠금은 결선 부재로 실패한다). 그 뒤 A → B 순으로 구현한다.
2. AC를 전부 실행한다. `npm test` 기준선은 1310 pass이며 추가한 케이스 수만큼만 늘어야 한다.
3. **가정 실측 프로브**(테스트가 아니라 관측 — 요약에 결과를 기록): 이 수정은 "리다이렉트를 따라간 응답 객체의 URL이 **최종** 주소를 담는다"는 가정 위에 있다. 스크래치패드에 **ASCII 경로**의 러너 파일을 만들어, 임시 포트 두 개로 (A: 302로 B를 가리킴 / B: health 성공 응답) 를 세우고 표준 fetch로 A를 호출해 응답 URL이 B를 가리키는지 확인하라. 확인 후 서버를 반드시 닫고 러너 파일은 리포에 남기지 마라. 리포 `news.db`·`uploads/`·실행 중인 서버에는 **절대 접속하지 마라**.
4. **미검증 정직 기록**: 이 환경에는 Electron 런타임에서 리다이렉트 배치를 실왕복시킬 수단이 없다. 3의 프로브는 **표준 fetch로 '리다이렉트 후 응답 URL이 최종 주소를 담는다'는 가정만 실측한 것이고, 실제 실행 경로는 Electron의 net.fetch**다(둘은 다른 구현이다). 요약에 그 구분을 그대로 적어라 — 예: "가정은 표준 fetch로 실측(응답 URL이 최종 주소), 실제 경로(Electron net.fetch)에서의 실왕복은 미검증. 잠금은 순수 단위 + 결선 텍스트 잠금까지." '검증했다'고 뭉뚱그리지 마라(phase 63~65의 unverified 기록 관행).
5. **변이 검증 3종**(각각 red 확인 후 원복):

   - (b) 저장 경로를 요청 origin으로 되돌리기 → 텍스트 잠금 (iii)가 red.
   - (c) 승격 규칙에서 자격증명 거부를 빼기 → 순수 함수 케이스가 red.

## 금지사항

- 리다이렉트 추종을 끄거나(수동 모드로 바꾸거나) 재시도·백오프·주기 확인을 넣지 마라. 이유: 프로브는 사용자 액션당 1회라는 ADR-008 계약이고, 추종을 끄면 정상적인 프록시 배치가 실패로 뒤집힌다 — 이 step은 **결과를 읽는 것**만 고친다.
- 실패 판정(도달 불가·상태 이상·기사작성기 서버 아님)일 때 승격하지 마라. 이유: 오류 페이지·캡티브 포털로의 리다이렉트가 저장 주소를 바꾸면 접속 불능이 영구화된다.
- 문자열 자르기·정규식으로 origin을 조립하지 마라. 이유: 포트 생략·IPv6·유니코드 호스트에서 조용히 틀린 origin이 나오고, 그 값이 동일 출처 판정과 secure-origin 스위치의 입력이 된다(모듈 상단 CRITICAL).
- 판정 로직을 메인 파일에 인라인으로 넣지 마라. 이유: 메인 파일은 Electron 의존이라 단위 테스트가 불가능하다 — 판정은 순수 모듈, 메인은 결선만이라는 계층 계약(ADR-011·phase 62~64 전례)이다.
- 메인 파일 주석에 텍스트 잠금 (iii)의 needle 표현식을 쓰지 마라. 이유: 그 스캔은 주석을 구분하지 않아 설명 한 줄이 잠금을 즉시 red로 만든다. red가 났을 때 **정규식을 느슨하게 풀지 말고 주석 쪽을 고쳐라**.
- 기존 진단 이벤트 이름·필드를 바꾸거나 지우지 마라(추가만 하라). 이유: 배포 검증 스크립트가 그 이벤트를 단언 대상으로 삼는 계약이다.
- 설정 화면(`client/pages/**`)에 새 안내 문구·새 브리지 함수를 추가하지 마라. 이유: 확인 응답의 origin이 이미 화면에 그대로 표시되므로 승격값이 자동 반영된다 — diff 대비 가치가 없다(decisions (18)).
- `docs/**`를 이 step에서 열지 마라(ADR-011 보강 포함). 이유: 문서 1문장 보강은 step5 소유다 — 코드 step이 문서를 함께 만지면 게이트를 통과한 코드와 문서가 다른 커밋 단위로 갈라진다.
- 서버 HTTPS 종단·PE 문자열 등 이월 항목을 함께 처리하지 마라. 이유: phase 64·65에서 제외 확정된 항목이다.
