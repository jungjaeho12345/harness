## 배경

로드맵 P3의 완료 게이트 셋째는 **"운영 cron tick 전환"** 이다. 현재 운영은 이렇다(`packaging/server/README-배포.md` 74~85행 실측): 앱에 타이머가 없으므로 **외부 cron(Windows 작업 스케줄러)이 `POST /api/login`으로 Z 세션을 얻고 `x-session-id` 헤더로 `POST /api/distribution/tick`을 호출**한다. 세션이 1시간 슬라이딩 만료라 **호출 때마다 로그인 → tick** 순서다.

전환 자체는 "스크립트의 `$base`를 바꾸는 것"처럼 보인다. **그러나 그렇게 적어서는 안 된다** — 확인해야 할 것이 최소 다섯이다:

1. Spring이 **`x-session-id` 헤더**를 실제로 받는가(`SessionTokens`가 쿠키 우선·헤더 폴백이지만 **실측하라**).
2. `Origin`·`Referer`가 없는 서버-서버 POST가 **CSRF 게이트를 통과**하는가(ADR-009의 의도된 관용 — Spring `CsrfOriginFilter`도 같은가).
3. **로그인 레이트리밋**(15분/10회)에 걸리지 않는가 — tick 주기가 짧으면 **매 호출마다 로그인**이 한도를 먹는다. 주기와 한도를 곱해 봐라(조사표 6번의 실제 주기로).
4. **컷오버 시각의 이중 실행**: 스케줄러가 Node와 Spring 양쪽을 부르는 구간이 생기면 중복 배부가 난다. **같은 host:port**를 쓰므로 URL은 그대로지만, **작업이 두 개 등록돼 있으면** 문제다.
5. **실패가 보이는가**: 지금 스크립트는 실패해도 조용할 수 있다. 전환을 계기로 **종료코드·로그**를 갖춘 형태로 개정한다.

## 작업

### A. Spring 대상 tick 왕복 실측

임시 Spring 인스턴스(임시 `DATA_DIR` · `DIST_SPOOL_DIR` 주입)에 대해 **현재 운영 스크립트와 같은 형태의 호출**을 그대로 재현하고 결과를 표로 남긴다:

- `POST /api/login`(Z) → 200 · 세션 획득 방식(응답 본문의 `sessionId`인지 쿠키인지 — **README의 예시가 `$login.sessionId`를 쓴다. 그 필드가 Spring 응답에도 있는지 실측하라**).
- `POST /api/distribution/tick` + `x-session-id` → 200 · 응답 shape(계약이 동결한 그대로) · **경로 비노출**.
- 같은 호출 **2회 연속** → 멱등(두 번째가 재배부하지 않는가 — 계약 케이스가 보는 축이지만 **운영 스크립트 경로로도** 확인하라).
- `Origin`/`Referer` **없이** 보낸 요청이 통과하는가(ADR-009 관용).
- 비-Z 세션으로 호출 → 403 · 무세션 → 401.
- `DIST_SPOOL_DIR` 미설정 인스턴스 → 503 `spool-disabled`.

**결과가 Node와 다르면 그것이 발견이다** — 같은 표를 Node 대상으로도 채워 **나란히** 적어라.

### A-2. [② 검토 반영 · 필수] 다중 인스턴스 중복 배부 실측

**이 전환은 ADR-012의 기계적 보호를 잃는다**(`src/db/instanceLock.js` 1~6행: Node의 잠금은 포트가 아니라 **`DATA_DIR` 범위**이고 그 근거에 **배부 스풀 기록**이 명시돼 있다. Spring에는 대응물이 0건이다). 초안은 이 위험을 절차로만 막았는데, **크기를 재지 않은 위험을 런북에 적으면 운영자가 심각도를 알 수 없다.** 그래서 여기서 잰다.

절차:

1. **Spring 인스턴스 2개**를 띄운다 — **서로 다른 포트** · **같은 MySQL 임시 DB** · **같은 `DIST_SPOOL_DIR`** · 같은 `DATA_DIR`(업로드 공유 상황 재현).
2. 두 인스턴스가 **둘 다 정상 기동하는지** 먼저 확인한다(Node라면 두 번째가 잠금에 막혀 뜨지 못한다 — **그 차이가 이 실측의 핵심**이다. Node로 같은 구성을 시도해 실제로 막히는지도 재서 나란히 적어라).
3. 시점 배부 대상 기사를 만들고 **양쪽에 tick을 호출**한다(동시·순차 두 경우).
4. **스풀 파일 수를 센다**: 중복이 나는가, 안 난다면 무엇이 막았는가(이력 기준 멱등이 DB 레벨에서 막을 수도 있다 — **그렇다면 그것이 좋은 소식이고 정확히 기록할 가치가 있다**). 중복이 난다면 **몇 개·어떤 이름**인지.
5. 같은 구성에서 **세션**도 본다: 한 인스턴스에서 로그인한 세션으로 다른 인스턴스에 요청하면 어떻게 되는가(세션 스토어가 프로세스 로컬이므로 401일 것이다 — **실측하라**). 이것은 로드밸런서를 앞에 두는 구성이 왜 불가능한지의 근거가 된다.

**산출물**: 실측표 + 그 결과를 반영한 **런북 §0 낭독 문구**와 **§10 분기 항목**(예: "서버가 두 개 떠 있지 않은지 확인하는 방법"). 실험은 **임시 DB·임시 스풀**에서만 한다.

### B. tick 스크립트 개정판

`packaging/server/`에 **Spring 대상 tick 스크립트**를 둔다(기존 README의 예시를 대체하는 것이 아니라 **나란히** 둔다 — 롤백 시 Node용이 필요하다). 요구:

- 자격은 **스크립트에 평문으로 두지 않는다**(현재 README도 그렇게 경고한다). Windows 자격 관리자·환경변수·권한을 좁힌 리포 밖 파일 중 하나를 택하고 **그 선택과 이유를 문서에 적어라**.
- **종료코드**: 0=성공, 비-0=실패(로그인 실패 / tick 비-200 / 네트워크). 스케줄러가 실패를 알 수 있어야 한다.
- **로그**: 실행 시각·결과·`distributed` 건수만. **세션 토큰·자격·스풀 경로를 로그에 남기지 마라**(tick 응답에 경로가 없는 것이 계약인데 로그에 남기면 그 계약을 밖에서 깬다).
- **이중 실행 방지**: 같은 스크립트가 겹쳐 도는 것을 막는다(단순 락 파일 또는 스케줄러 설정 — **앱 안에 락을 만들지 마라**).
- **주기**: 조사표 6번의 현재 주기를 유지하되, **로그인 레이트리밋과의 곱**을 계산해 문서에 적는다. 한도에 근접하면 주기를 늘리거나 세션 재사용을 검토하라(세션 재사용은 1시간 슬라이딩이라 가능하다 — 다만 **세션을 파일에 저장하면 그것이 토큰 유출 표면**이다. 트레이드오프를 적어라).

- 1번은 **자동 판정**이어야 한다(사람이 눈으로 200을 보는 것은 AC가 아니다). Node·Spring 두 대상 표가 산출물로 남는다.
- `server-spring/src/main`은 이 step에서 **0줄** 바뀌는 것이 기본이다. 바뀌었다면 왜인지 적어라(예: 실측 결과 헤더 폴백이 없더라 → 그건 **계약 위반**이므로 별도 판단이 필요하다).
- **변이 전건 결과표(필수)** — 최소 5종:
  - **S1** tick 스크립트에서 `x-session-id` 헤더 제거 → 기대: 401. 검증 스크립트가 잡는가.
  - **S2** Z가 아닌 계정으로 로그인 → 기대: 403. (인가가 세션에서 도출되는지 — ADR-004.)
  - **S3** tick을 2회 연속 호출 → 기대: 두 번째에 재배부 0. **실제 스풀 파일 수로 확인**하라(응답만 보면 멱등을 못 본다).
  - **S4** 스크립트의 종료코드 처리를 제거(항상 0) → 기대: 실패가 스케줄러에 보이지 않게 된다 — 검증이 그것을 잡는가. 못 잡으면 그 자체가 공백이므로 기록하라.
  - **S5** 자격을 스크립트에 평문으로 박음 → 기대: 비밀 위생 게이트/리뷰가 잡는가(`SecretHygieneTest`의 스캔 범위에 `packaging/**`이 들어가는지 **실측**하라 — 안 들어가면 그 사실이 공백이고, 넣을지 여부는 별도 판단이다).
  - **S6** **[② 검토 반영]** 같은 구성으로 **Node** 인스턴스를 2개 띄워 본다(같은 `DATA_DIR`) → 기대: **두 번째가 ADR-012 잠금에 막혀 뜨지 못한다**. 이 '변이'는 코드를 고치는 것이 아니라 **잃은 보호를 눈으로 확인하는 대조 실험**이다 — Spring 2개는 뜨고 Node 2개는 안 뜬다는 비대칭이 A-2 실측표의 첫 줄이다.
  - 각 변이에 기대/실제/원복 확인.
- **A-2 실측표(필수)**: Spring 2개 기동 성공 여부 · tick 양쪽 호출 후 **스풀 파일 수**(중복 유무와 개수) · 교차 세션 요청 결과 · Node 2개 기동 시도 결과. **"아마 중복될 것이다"로 적지 마라 — 숫자로 적어라.**
- **레이트리밋 산술 기록**: `현재 주기 × 15분 내 호출 수 vs 한도 10회` 계산을 숫자로 적는다.

## 검증 절차

1. 임시 Spring 인스턴스에서 A의 6항을 전부 돌리고, **같은 6항을 Node 인스턴스에서도** 돌려 표를 나란히 만든다.
2. 스풀 파일 수로 멱등을 확인한다(응답 필드만 믿지 마라).
3. 스케줄러 등록은 **사용자 실행 항목**이다 — 에이전트는 명령과 판정 방법만 문서에 남긴다.
4. 실행 전후 리포 자산 지문 대조.

## 되돌림 절차

- 리포 되돌림: 새 스크립트·문서 추가분 제거(앱 코드 0줄).
- **운영 되돌림**(런북이 소유): 스케줄러에서 Spring용 작업을 끄고 Node용 작업을 되살린다. **tick 작업은 언제나 정확히 하나만 활성**이어야 한다 — 둘 다 켜면 같은 기사가 두 번 배부될 수 있다(중복 스풀은 ADR-008 트레이드오프가 '미발송보다 낫다'고 판단한 방향이지만, **의도하지 않은 중복은 다르다**).

## 금지사항

- **앱 안에 타이머·스케줄러·상주 루프를 만들지 마라.** 이유: ADR-008 (3)이 tick을 pull로 정한 이유가 그것이고, `Adr008DisciplineTest`의 '주기 실행' 군은 예외가 0이다.
- **`RoutePolicy`·계약 케이스를 고치지 마라.** 이유: tick의 인가 등급과 응답 shape은 동결이다.
- **자격을 스크립트·리포·로그·argv에 남기지 마라.** 이유: tick은 **Z(관리자) 자격**이다 — 유출되면 전 기능이 열린다.
- **tick 작업을 '추가'하지 마라 — '교체'하라.** 이유: 두 작업이 동시에 살아 있으면 중복 배부다.
- **응답만 보고 멱등을 판정하지 마라.** 이유: 스풀 파일이 실제로 몇 개 생겼는지가 사실이다.
- **레이트리밋을 우회하려고 서버 설정을 바꾸지 마라.** 이유: 로그인 한도는 보안 경계다. 주기를 바꾸거나 세션 재사용을 택하고 그 트레이드오프를 적어라.
