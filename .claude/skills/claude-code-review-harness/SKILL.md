# Claude Code 리뷰 하네스

## 목표

코드 변경사항을 검토해 실제 리스크가 있는 문제를 찾고, 사용자가 바로 수정할 수 있는 구체적인 리뷰 코멘트를 작성한다.

이 스킬은 다음 작업에 집중한다.

- 변경 의도와 실제 diff 비교
- 잠재 버그, 회귀, 보안, 성능, 동시성, 데이터 무결성 문제 탐지
- API 계약, 타입, 에러 처리, 경계 조건 검토
- 테스트 누락과 테스트 품질 평가
- severity가 있는 리뷰 결과 작성
- 불필요한 취향성 코멘트 제거

## 기본 원칙

1. 중요한 문제를 우선한다.
   - correctness, security, data loss, production incident 가능성을 최우선으로 본다.
2. 근거 없는 지적을 하지 않는다.
   - 문제가 되는 코드 위치, 실패 가능한 시나리오, 영향 범위를 함께 설명한다.
3. 취향성 스타일 리뷰를 남발하지 않는다.
   - 프로젝트 컨벤션 위반이나 유지보수 리스크가 있을 때만 언급한다.
4. 리뷰와 테스트 실행 여부를 분리한다.
   - 테스트를 실행하지 않았다면 “정적 리뷰만 수행”이라고 말한다.
5. 좋은 변경은 인정하되, 최종 출력은 사용자가 조치할 내용 중심으로 쓴다.

## 작업 흐름

### 1. 변경 범위 파악

먼저 변경 파일과 diff를 확인한다.

```bash
git status --short
git diff --stat
git diff
```

diff가 너무 크면 파일별로 나눠 본다.

```bash
git diff -- path/to/file
```

필요하면 최근 커밋 기준 비교도 사용한다.

```bash
git diff HEAD~1..HEAD
```

단, 사용자의 작업 트리를 바꾸는 명령은 실행하지 않는다.

### 2. 변경 의도 추론

다음을 기준으로 변경 의도를 정리한다.

- 어떤 기능 또는 버그를 다루는가
- 어떤 공개 API, DB 스키마, 설정, 권한, 상태 흐름이 바뀌었는가
- 기존 동작과 호환성이 유지되는가
- 테스트가 변경 의도를 충분히 설명하는가

의도가 불명확하면, 리뷰 결과에서 “확인 필요”로 표시하고 성급히 단정하지 않는다.

### 3. 리뷰 체크리스트

#### Correctness

- null/undefined/None 처리 누락
- 빈 배열, 빈 문자열, 0, false 같은 falsy 값 처리 오류
- off-by-one, timezone, locale, encoding 문제
- 잘못된 조건문 또는 early return
- 예외 처리 누락
- async/await, promise, coroutine 처리 누락
- race condition 또는 stale state
- 기존 API 계약 위반

#### Security

- 인증/인가 우회 가능성
- 사용자 입력 검증 누락
- SQL/NoSQL/command injection 가능성
- XSS, SSRF, path traversal 가능성
- 민감 정보 로그 출력
- 토큰, 키, secret 하드코딩
- 권한 범위가 과도하게 넓어진 변경

#### Data integrity

- 데이터 손실 가능성
- 중복 생성, 중복 결제, 중복 요청 처리 문제
- transaction 누락
- migration backward compatibility 문제
- partial failure 처리 누락
- idempotency 문제

#### Performance

- N+1 query
- 불필요한 전체 스캔
- 반복문 내부 네트워크/DB 호출
- 캐시 무효화 문제
- 메모리 사용량 급증
- hot path에서 비싼 계산 반복

#### Maintainability

- 책임이 과도하게 커진 함수/클래스
- 이름과 실제 동작 불일치
- 중복 로직 증가
- 숨겨진 side effect
- 불명확한 에러 메시지
- 테스트하기 어려운 구조

#### Tests

- 핵심 성공 경로 테스트 존재 여부
- 실패/예외 경로 테스트 존재 여부
- 경계값 테스트 여부
- 회귀 테스트가 실제 버그를 잡는지 여부
- mock이 실제 동작과 어긋나지 않는지 여부
- snapshot이 의미 있는지 여부

### 4. Severity 기준

리뷰 코멘트는 가능하면 severity를 붙인다.

#### Critical

즉시 수정하지 않으면 보안 사고, 데이터 손실, 대규모 장애, 결제/권한 문제로 이어질 가능성이 높다.

#### High

주요 기능 장애, 실제 사용자 영향, 심각한 회귀 가능성이 있다.

#### Medium

특정 조건에서 버그가 발생하거나 유지보수 비용이 커질 가능성이 있다.

#### Low

명확성, 테스트 보강, 작은 리팩터링 등 개선 가치가 있으나 즉시 장애 가능성은 낮다.

#### Nit

프로젝트 컨벤션에 맞춘 사소한 제안이다. Nit는 많아도 1~2개만 남긴다.

## 리뷰 코멘트 작성법

좋은 리뷰 코멘트는 다음 요소를 포함한다.

1. 문제가 되는 위치
2. 실패 가능한 구체적 시나리오
3. 왜 중요한지
4. 수정 방향 또는 예시

형식:

```markdown
### [High] 제목

- 위치: `path/to/file.ext:line`
- 문제: 무엇이 잘못될 수 있는지
- 근거: diff 또는 코드 흐름상 왜 그렇게 되는지
- 영향: 사용자/시스템에 어떤 문제가 생기는지
- 제안: 어떻게 고칠지
```

코드 제안이 짧으면 예시를 포함한다.

```markdown
제안 예시:

```ts
if (!user) {
  throw new UnauthorizedError();
}
```
```

단, 확실하지 않은 대규모 리팩터링 코드는 장황하게 작성하지 말고 방향만 제시한다.

## 최종 리뷰 출력 형식

```markdown
## 리뷰 요약

- 전체 판단:
- 가장 큰 리스크:
- 테스트 관점:

## 발견한 문제

### [Severity] 문제 제목

- 위치:
- 문제:
- 영향:
- 제안:

## 테스트 보강 제안

- 어떤 케이스를 추가해야 하는지:
- 이유:

## 확인하지 못한 부분

- 실행하지 않은 테스트:
- 코드만으로 판단하기 어려운 전제:
```

문제가 없으면 다음처럼 말한다.

```markdown
## 리뷰 결과

중대한 correctness/security/data integrity 문제는 발견하지 못했습니다.

다만 아래 사항은 확인하면 좋습니다.

- 테스트 실행 여부:
- 남은 리스크:
```

## 좋은 리뷰를 위한 판단 기준

- “가능성”만 있는 문제는 재현 조건을 함께 제시한다.
- 단순 스타일 지적보다 실제 장애 가능성을 우선한다.
- 테스트 누락은 “어떤 입력에서 어떤 실패를 잡아야 하는지”까지 적는다.
- 코드가 이미 방어하고 있는 문제를 중복 지적하지 않는다.
- 프로젝트 컨벤션이 명확하지 않으면 단정하지 않는다.

## 테스트 스킬과의 역할 분담

이 스킬은 정적 리뷰와 리스크 판단을 담당한다.

다음 상황에서는 테스트 스킬을 함께 사용한다.

- 리뷰 중 발견한 문제가 실제로 재현되는지 확인해야 할 때
- 실패하는 테스트 로그를 분석해야 할 때
- 수정 후 검증 명령을 실행해야 할 때
- 회귀 테스트를 작성하고 실행해야 할 때

리뷰 결과에는 테스트 실행 여부를 명확히 적는다.

예시:

- “정적 리뷰만 수행했으며 테스트는 실행하지 않았습니다.”
- “관련 단위 테스트 실행은 테스트 스킬의 범위입니다.”
- “이 이슈는 테스트로 재현 가능해 보이며, 회귀 테스트 추가를 권장합니다.”

## 금지 사항

- 실행하지 않은 테스트를 실행했다고 말하지 않는다.
- 근거 없는 보안 취약점 주장을 하지 않는다.
- 취향성 리팩터링을 중대한 문제처럼 표현하지 않는다.
- diff 밖의 코드를 충분히 보지 않고 전체 설계를 단정하지 않는다.
- 단순히 “좋아 보입니다”로 끝내지 말고 확인 범위와 남은 리스크를 적는다.
