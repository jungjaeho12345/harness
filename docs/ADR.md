# Architecture Decision Records

## 철학
외부 의존성을 최소화하고 언어/런타임 표준 기능을 우선한다(런타임 의존성은 Express와 보안 미들웨어뿐, DB·번들러·테스트는 내장/표준 도구 사용). 빌드 도구(프론트 vite, 서버 배포 패키징의 esbuild·postject)는 devDependency이며 배포물에 들어가지 않는다 — 이 원칙은 **런타임 의존성** 축의 것이고 빌드 도구 축과 구분한다(ADR-010). 빌드/실행 셸 전용 devDependency 축에는 클라이언트 데스크톱 셸의 electron도 포함된다(ADR-011). 모든 기능은 테스트를 먼저 작성(TDD)하고 작동하는 최소 구현을 선택한다. 
신뢰 경계는 서버에 둔다 — 클라이언트가 보낸 값(특히 권한)은 신뢰하지 않는다. 
DB의 데이터는 절대 삭제하지 않는다(비파괴·멱등 마이그레이션만 허용).

---

### ADR-001: Vite + React SPA + 독립 Express API 서버 (Next.js 풀스택 대신)
**결정**: 프론트엔드는 Vite로 빌드하는 순수 클라이언트 React 19 SPA(`:5173`), 백엔드는 별도 Express REST/SSE 서버(`127.0.0.1:3001`)로 분리한다. 두 계층은 HTTP로만 통신한다.
**이유**: 사내 기사 작성 도구라 SEO/SSR 이점이 없다. SPA + 얇은 API 서버로 분리하면 프론트/백 경계가 명확해지고, API 서버를 테스트에서 in-memory 의존성으로 주입할 수 있다. Vite는 설정이 가볍고 HMR이 빠르다.
**트레이드오프**: SSR 대비 first-paint가 느리고 SEO가 불가하다. 두 origin 간 CORS와 세션 헤더(`x-session-id`) 전파 배선을 직접 관리해야 한다.

### ADR-002: Node.js 내장 SQLite(`node:sqlite`) + 직접 SQL (외부 DB/ORM 대신)
**결정**: 데이터는 Node 22의 내장 모듈 `node:sqlite`(`DatabaseSync`)로 단일 파일 `news.db`에 저장한다. ORM 없이 모델 계층에서 직접 SQL을 쓰고, User/Article/Contents 3개 테이블만 둔다(FK 미선언, 정합성은 애플리케이션이 유지).
**이유**: 외부 DB 서버·드라이버·ORM 의존성을 0으로 만든다. 단일 파일이라 백업/이식이 쉽고, 테스트는 in-memory DB로 빠르게 격리된다. 스키마 변경은 `CREATE TABLE IF NOT EXISTS`/additive `ALTER`만 사용해 기존 데이터를 보존한다(DB 비파괴 원칙).
**트레이드오프**: `--experimental-sqlite` 플래그와 Node ≥22.5가 필요한 실험적 API다. 동시 쓰기·수평 확장이 불가하고, 마이그레이션과 참조 정합성을 애플리케이션이 직접 책임진다.

### ADR-003: 주입 가능한 Model 계약으로 전송 계층 추상화 (프론트엔드 MVC)
**결정**: 프론트엔드를 Model/View/Controller로 분리하고, Model을 `freeze`된 메서드 집합(`MODEL_KEYS`)을 따르는 주입형 인터페이스(`contract.js`)로 정의한다. 실제 REST/SSE 배선은 `httpModel` 뒤에 격리하고, 테스트는 `fakeModel`을 주입한다.
**이유**: View/Controller를 transport-agnostic하게 유지하면 UI 로직을 실제 네트워크 없이 단위 테스트할 수 있다. 이 계약이 프론트와 백엔드 서비스 계약을 잇는 단일 통합 seam이 되어, 응답 shape 불일치를 한 곳에서 검증할 수 있다.
**트레이드오프**: 계약이라는 간접 계층이 추가되고, 백엔드 응답 shape과 `MODEL_KEYS`를 수동으로 동기화해야 한다(JS라 타입 강제가 없다).

### ADR-004: 세션 기반 서버측 인가 — 역할은 세션에서만 도출 (클라이언트 role 불신)
**결정**: 모든 보호된 라우트의 acting role은 `x-session-id`로 검증한 서버 세션에서만 도출하고, `req.body.role`은 신뢰하지 않는다. 세션은 1시간 슬라이딩 idle 만료를 가지며, R(기자)/D(데스크)/Z(관리자) 역할 게이트로 편집 잠금·송고/보류/킬·사용자/수신설정 관리를 강제한다.
**이유**: 클라이언트가 보낸 역할 값을 신뢰하면 권한 상승이 가능하다. 신뢰 경계를 서버에 두어 인가를 단일 지점에서 강제하고, 비밀번호는 bcrypt 해시로 저장한다. helmet(CSP)·CORS allowlist·로그인 레이트리밋으로 표면을 추가로 좁힌다. 세션 신원(role/active 등)은 **로그인 시점 스냅샷이 아니라 매 요청 User 행 재조회로 재도출**한다(세션 가드가 세션 스토어를 감싸고, 합성 루트가 모든 소비처에 그것만 주입한다) — 행이 없거나 `active='N'`이면 그 세션을 즉시 무효화한다.
**트레이드오프**: 서버 세션 스토어가 필요하다(현재 in-process라 다중 인스턴스 시 공유 스토어로 교체해야 함). 세션ID가 HttpOnly 쿠키가 아닌 헤더 방식이라 쿠키 전환·HTTPS 강제 등 추가 하드닝이 후속 과제로 남는다. 재도출 대가로 인증된 요청마다 User PK 조회가 1회 늘고(in-process SQLite, 마이크로초) DB 장애가 인가 게이트에서 먼저 드러나지만, 비활성화·역할 강등이 재로그인 없이 즉시 반영된다(캐시·TTL 없음).

### ADR-005: SSE 단방향 무효화 스트림으로 실시간 동기화 (WebSocket 대신)
**결정**: 기사 생성/수정/상태전이/편집잠금 변경을 서버 in-process `EventEmitter` → SSE(`/api/stream`)로 브로드캐스트한다. 페이로드는 행 데이터가 없는 "무효화 신호"이며, 클라이언트가 자기 필터로 재조회한다.
**이유**: 동기화는 서버→클라이언트 단방향이면 충분하다(클라이언트 변경은 일반 REST로 올라간다). SSE는 표준 `EventSource`로 추가 의존성 없이 자동 재연결을 제공한다. 행 없는 신호 방식이라 역할별 데이터 노출 문제를 회피한다.
**트레이드오프**: 양방향 통신은 불가하다(필요해지면 WebSocket으로 교체). 신호마다 클라이언트 재조회가 발생한다(서버측 필터링 없는 naive broadcast). `EventSource`가 커스텀 헤더를 못 보내 이 라우트의 인증 수단은 **HttpOnly 세션 쿠키(withCredentials)** 뿐이다 — 과거의 `?session=` 쿼리 폴백은 서버·클라이언트 양쪽에서 제거됐고(평문 토큰 URL 누출 표면 금지, ADR-007과 같은 규율) 그 대가로 cross-origin dev 구성에서는 SSE 인증이 불가하다(동일 출처 프록시 배치를 쓴다). 이 스트림도 로그 SSE와 동일하게 **push 시점 재검증(비연장 peek)** 을 적용한다 — 무효화된 세션에는 `change` 신호를 쓰지 않고 `event: unauthorized` 1회 후 연결을 끝낸다.

### ADR-006: 얇은 transport + 계층형 도메인 백엔드 (controllers → services → models)
**결정**: `server/index.js`는 비즈니스 로직 없는 얇은 REST/SSE 라우팅만 담당하고, 도메인 로직은 `controllers → services → models → db` 계층에 둔다. 모든 의존성은 주입 가능하게 만들어 테스트에서 in-memory로 대체한다.
**이유**: 전송(HTTP)과 도메인 로직을 분리하면 로직을 HTTP 없이 직접 테스트할 수 있고, 라우트는 shape 매핑과 인가 게이트만 검증하면 된다. 광범위한 테스트 스위트(`node --test` / Vitest)가 회귀를 막는다.
**트레이드오프**: 파일·계층 수가 많아져 작은 변경도 여러 계층을 거친다. 계층 간 계약을 수동으로 유지해야 한다.

### ADR-007: 관리자용 로그 SSE는 실데이터를 push (ADR-005 무효화 신호 원칙의 예외)
**결정**: 관리자용 실시간 로그 뷰어를 위해 `GET /api/logs/stream`(SSE)으로 **로그 라인 실데이터**(record `{ seq, ts, level, message, line }`)를 push하고, `GET /api/logs/digest`로 24시간 창(전날 06:00 ~ 당일 05:59:59.999 KST)을 pull한다. 로그는 **in-memory 링 버퍼**에만 보존한다(파일/DB 미저장). 두 엔드포인트는 **세션 role Z 전용**이다(미인증 401, 비-Z 403 — 로그인만 요구하는 `/api/stream`과 다르다). 스트림은 접속마다 버퍼 최근 2000건을 replay한 뒤 실시간을 잇고(Last-Event-ID 미구현, 중복은 클라이언트가 `seq`로 필터), EventSource 인증은 **HttpOnly 세션 쿠키(withCredentials)**로 한다 — 쿼리스트링에 토큰을 싣지 않는다(평문 토큰 URL 누출 표면 금지, 기존 `?session=` 폴백은 이미 제거됨).
**이유**: ADR-005의 "행 데이터 없는 무효화 신호" 원칙은 역할별 데이터 노출을 피하기 위함인데, 로그는 그 자체가 표시 대상이라 신호만으로는 불가능하다. Z 전용 게이트로 노출을 봉인해 위험을 좁힌다(role은 검증 세션에서만 도출 — ADR-004). zero-dep(log4j 스타일 자체 구현)으로 ADR 철학을 지키고, LOGS.md "파일 미저장" + DB 비파괴(무한 증식 방지)를 지킨다. LOGS.md의 "전날 하루부터 오전 5시 59분까지"는 **06:00 정렬 24시간 창 [D-1 06:00, D 06:00)** 으로 확정 해석한다.
**트레이드오프**: 서버 재시작 시 버퍼가 유실된다. cap(10000줄) 초과 시 오래된 로그가 evict되어 다이제스트가 일부를 놓칠 수 있다. 다이제스트의 매일 6시 전달은 앱이 아니라 운영 루틴이 pull로 수행한다(앱에 타이머/외부 egress 없음). 접속 시점 인증만으로는 로그아웃·만료·강등·비활성화 이후에도 push가 계속되던 문제(Z 전용 봉인이 시간축에서 깨짐)를 **push 시점 재검증(비연장 peek — `touch`면 열린 스트림이 세션을 무한 연장한다)** 으로 닫았고, 무효화 이후에는 로그가 단 한 줄도 전송되지 않는다(`event: unauthorized` 1회 후 종료). 다만 이벤트가 없으면 연결 종료가 다음 이벤트까지 지연된다 — 주기 재검증 타이머를 두지 않기 때문이다(ADR-008).

### ADR-008: 배부(distribution)는 파일 스풀 outbound + tick pull — 앱 내 타이머/외부 egress 금지 유지
**결정**: 배부 시스템(2026-07-26 스코프 확장)은 수집의 대칭 구조로 구현한다. (1) 전송 수단은 **파일 스풀 outbound** — 앱은 배부 스풀 디렉토리(수신처별 하위 폴더)에 기사 파일(JSON, markupVersion 포함)을 쓰기만 하고, 실제 발송은 외부 전송기가 담당한다(앱은 네트워크 egress 없음). (2) 배부 대상은 신규 **DistributionTarget** 테이블(kind=언론사|비언론사)로 관리한다 — ReceiverConfig는 수집(inbound) 전용이라 재사용하지 않는다. (3) 시점 배부(엠바고 1·2차 시각)는 앱 내 타이머가 아니라 **`POST /api/distribution/tick`(Z/시스템 전용) pull 엔드포인트**로 실행한다 — 외부 운영 루틴이 주기 호출한다. (4) 엠바고 없는 일반 기사(DPS)도 송고 즉시 언론사+비언론사 전체에 배부하고 `Contents.distributedAt`을 기록한다. (5) 배부 이벤트는 ArticleHistory에 기록하고, 엠바고 기사의 배부가 전부 완결되면 EPS→DPS로 전이한다. (6) 수신처 단위 배부 실패는 ArticleHistory에 append-only로 영속하고(additive 컬럼만 — 행 삭제·수정 없음), 미발송의 복구는 Z가 명시적으로 실행하는 재전송(해당 수신처로의 스풀 파일 재기록)뿐이다 — 앱은 자동 재시도·백오프·재시도 큐를 두지 않으며((1)·(3)의 "앱에 타이머·egress 없음" 원칙 유지), 해소 여부는 실패 행을 갱신하지 않고 이후 재전송 이력으로 파생한다.
**이유**: 수집이 "외부 FTPd가 스풀에 드롭 → 앱은 fs.watch"인 것과 동형으로, 배부도 "앱이 스풀에 드롭 → 외부 전송기가 발송"이면 앱에 네트워크 egress·재시도·타임아웃 복잡성이 생기지 않고 오프라인 테스트가 결정적이다. tick pull은 ADR-007의 "앱에 타이머/외부 egress 없음" 원칙을 유지한다(로그 다이제스트 pull과 동형). news.md 엠바고 규칙(1차→언론사, 2차→비언론사·송고 시 언론사 즉시, 1+2차 조합)이 유일한 실질 스펙이며, 위 결정들은 2026-07-26 사용자 확정이다.
**트레이드오프**: 실제 발송 성공/실패를 앱이 알지 못한다(스풀 기록 시각=distributedAt — 발송 완료가 아니라 배부 지시 완료다). 시점 배부의 정시성이 외부 tick 호출 주기에 의존한다. 외부 전송기와 운영 cron이 별도 운영 요소로 필요하다. 미발송의 복구가 운영자의 관측·조작에 의존하며(자동 복구 없음), 실패 해소 판정이 안전 방향(과다 보고)이라 이미 복구된 항목이 목록에 남을 수 있고 그 상태에서 재전송하면 같은 수신처에 중복 스풀이 생길 수 있다 — 미발송보다 중복이 낫다는 판단이다. 단 재송고로 새 배부 사이클이 열린 기사에서는 이전 사이클의 실패 행으로 재전송할 수 없다(stale-cycle 거부 — 엠바고가 재설정된 기사의 미도래 유출 차단이 우선이며, 그 미발송의 복구는 새 사이클의 배부·실패 기록으로만 이어진다).

### ADR-009: CSRF 방어는 상태 변경 메서드의 Origin/Referer allowlist 검증 (CSRF 토큰·SameSite 변경 대신)
**결정**: `GET`/`HEAD`/`OPTIONS`를 제외한 모든 요청에 대해 전역 미들웨어(`csrfOriginGuard`)가 주장 출처를 검증한다. 주장 출처는 `Origin` 헤더, 없으면 `Referer`의 origin(파싱 실패 시 거부)이다. **자기 출처**(`${req.protocol}://${req.get('host')}`) · **허용 목록**(`allowedOrigins()` — `ALLOWED_ORIGINS` 콤마 목록. 기본값 `http://localhost:5173`·`http://127.0.0.1:5173`는 **비프로덕션에서만** 앞에 붙고, **프로덕션 기본값은 빈 목록**이다) · **비프로덕션의 loopback 출처**(localhost/127.0.0.1/[::1], 포트 무관)만 통과시키고, 그 외(`Origin: null` 포함)는 `403 { ok:false, reason:'forbidden-origin' }`이다. 허용 목록은 CORS 옵션과 **단일 출처**를 공유한다. CSRF 토큰(double-submit cookie)은 도입하지 않고, 세션 쿠키의 SameSite/Secure 정책도 바꾸지 않는다. 미들웨어는 요청 로거 뒤(거부도 액세스 로그에 남는다) · 라우트 앞에 등록한다.
**이유**: CORS는 simple request(본문 없는 POST 등)의 **실행**을 막지 않고 **응답 읽기**만 막는다 — 프로덕션 세션 쿠키가 `SameSite=None; Secure`로 발급되므로 잠금 강제 해제·배부 대상 비활성화·tick·로그아웃 같은 부수효과 라우트가 cross-site에서 피해자 쿠키와 함께 실행될 수 있었다. 브라우저는 Fetch 표준상 비-GET 요청에 `Origin`을 항상 붙이고 공격자는 이를 생략시킬 수 없으므로 출처 검증이 유효한 방어다. 기존 CORS allowlist가 `localhost:5173` 고정이라 별도 출처 SPA 배포는 이미 preflight 단계에서 동작하지 않는다. 토큰 방식은 발급·저장·클라이언트 전 REST 경로 첨부·SSE 예외까지 전면 개조가 필요해 회귀 표면이 훨씬 크다.
**가정과 실패 모드**: 이 결정은 **동일 출처 배포를 전제**한다(리버스 프록시가 SPA와 `/api`를 같은 출처로 묶거나, 앱 자체의 SPA 서빙(phase 60)이 그 역할을 하는 배치). 앱은 `SPA_DIR`(기본 `web/dist`, `index.html` 부재 시 비활성)이 있으면 SPA 번들을 같은 출처에서 서빙한다 — 빌드 산출물은 그대로 정적 서빙하고, **매칭 파일이 없는** `GET`/`HEAD` 요청 중 경로가 `/api`·`/uploads`가 아니고 `Accept`에 `text/html`이 있는 것만 `index.html`로 폴백한다(경로 비교는 대소문자 무관). 정적 마운트는 이제 `/uploads`와 SPA 루트 둘이다. 이 배치에서는 자기 출처 판정만으로 쓰기가 통과하므로 `ALLOWED_ORIGINS`가 빈 목록인 것이 정상 구성이다. 별도 출처로 SPA를 띄우거나 프록시가 Host를 재작성하는 배포에서는 `ALLOWED_ORIGINS`를 명시 설정해야 하며, **미설정 시 프로덕션의 모든 쓰기 요청이 403**이 된다. 이 실패는 조용하다(로그인·조회는 되고 저장·송고만 막힌다) — 그래서 부트 시점에 허용 목록이 비면 경고를, 있으면 실제 적용 목록을 로그로 남긴다(`logOriginDiagnostics`). 부팅은 막지 않는다: 동일 출처 배포는 빈 목록이 정상 구성이다.
**트레이드오프**: `Origin`·`Referer`가 **모두 없는** 요청은 통과시킨다 — 서버-서버 클라이언트(수집 인제스트, 배부 tick cron, 테스트의 node 클라이언트)를 보존하기 위한 의도된 관용이며, 그 대가로 아주 오래된 브라우저의 form POST는 방어 밖이다. 비프로덕션 loopback 관용 때문에 `vite --host`로 LAN IP(`http://192.168.x.x:5173`)에서 띄우는 모바일 실기 테스트는 loopback이 아니라 비프로덕션에서도 쓰기가 403이 된다(그 경우 `ALLOWED_ORIGINS` 설정이 필요하다). `X-Forwarded-Host`는 신뢰하지 않는다(스푸핑으로 자기 출처 판정을 통과시킬 수 없게 `req.hostname` 대신 `req.get('host')`를 쓴다). 상태를 바꾸는 GET 라우트를 새로 만들면 이 방어 밖이다. 라우트별 예외 목록은 두지 않는다(예외 항목이 곧 우회 경로가 된다).

### ADR-010: 서버 배포는 Node SEA 단일 실행 파일 — esbuild·postject 번들 도구는 빌드 전용 의존성
**결정**: Windows 서버 배포는 Node **SEA(Single Executable Application)** 단일 exe(`기사작성기-server.exe`)로 한다. SEA가 요구하는 "단일 CJS 스크립트"는 **esbuild**로 서버 ESM 다중 파일을 번들해 만들고, SEA blob은 **postject**로 node.exe 사본에 주입한다(`npm run dist:server` — scripts/sea-build.mjs·dist-server.mjs). 두 도구는 **devDependencies**이며 런타임 의존성은 5개(express·helmet·cors·express-rate-limit·bcryptjs) 그대로다(추가 0). 패키지 배치 여부는 런타임 탐지(`node:sea`의 isSea 등)가 아니라 **엔트리(`server/main.js`)가 `bootstrap({ packaged: true })`로 명시 주입**하고, 데이터·SPA 경로는 exe 위치 기준(`<exe 디렉토리>/data`·`/web`)으로 해석한다(단일 출처: `resolveRuntimePaths()` 순수 함수). SEA 절차가 실패할 경우의 폴백은 node.exe 동봉 폴더(`--fallback` 명시 플래그 — 자동 폴백 금지)다. 2026-08-12 실측: SEA 성공(폴백 불사용), 한글 파일명 정상, 내장 Node v24.16.0.
**이유**: 서버 머신에 Node 설치·버전 관리·`npm install`을 요구하지 않기 위함이다(배포물 = exe + 정적 파일, 백업 = `data/` 폴더 복사). 5개 런타임 의존성이 전부 순수 JS라 네이티브 모듈 재빌드 문제가 없고(실측 — 비내장 동적 require 0건), DB가 내장 `node:sqlite` 단일 파일이라 외부 서비스 의존이 없다(ADR-002). 철학의 "외부 의존성 최소화"는 **런타임** 축의 원칙이다 — 빌드 도구는 배포물에 들어가지 않으므로 그 축이 아니며, esbuild는 이미 vite의 전이 의존으로 존재하던 것을 명시 고정한 것이다. 명시 주입을 택한 이유: 순수 함수 단위 테스트가 SEA 없이 두 배치를 모두 잠글 수 있고, 런타임 탐지는 번들러·Node 버전에 따라 조용히 뒤집힐 수 있다.
**트레이드오프**: exe에 Node 런타임이 통째로 들어가 파일이 크다(실측 89.5MB). 빌드 머신의 Node 버전이 배포물에 고정되어 보안 패치에 재빌드가 필요하다. SEA는 실험적 기능이라 Node 업그레이드 시 절차가 깨질 수 있다(그래서 폴백 경로를 남긴다). 스택 추적이 번들 좌표로 나온다. 서명되지 않은 exe는 SmartScreen 경고를 띄운다(코드 서명은 범위 밖). 크로스 컴파일은 불가하다(빌드 머신 node.exe를 복사하므로 빌드 머신 = 배포 대상 플랫폼). CJS 번들에서 `import.meta`가 빈 객체가 되므로 서버 모듈은 그 참조를 모듈 스코프 1곳으로 제한하는 규율이 필요하다(빌드 게이트가 경고 1건 초과를 실패로 잠근다).

### ADR-011: 데스크톱 클라이언트는 Electron 접속형 셸 — 백엔드·DB 미내장, 원격 페이지에 Node 권한 0
**결정**: Windows 클라이언트는 Electron 셸이 서버 origin을 `loadURL`만 하는 **접속형**으로 한다(`npm run dist:client` → `dist/기사작성기/` 무설치 포터블 폴더). 서버 주소는 최초 실행 시 셸 로컬 화면에서 입력받아 `GET /api/health`의 본문 `{ ok:true }`까지 확인한 뒤에만 `%APPDATA%\기사작성기\config.json`(화이트리스트 파싱 — 세션·자격증명 필드 없음)에 저장한다 — 확인 요청이 리다이렉트로 다른 출처에 도달했으면 저장·표시되는 값은 입력 주소가 아니라 리다이렉트를 따라간 **최종 origin**이고 재시작 안내·secure-origin 스위치도 그 값을 대상으로 하며, 확인 실패거나 최종 URL이 비정상(파싱 불가·http/https 밖 스킴·자격증명 포함·https 입력의 http 하향)이면 승격하지 않고 사용자가 입력한 주소를 유지한다(fail-safe — phase 66). 창은 **원격 앱 창(preload 없음)**과 **셸 로컬 창(preload 있음, 원격 내비게이션 전면 금지)** 둘로 분리한다. `setWindowOpenHandler`는 `about:blank`(SPA 상세보기·인쇄 창)와 동일 출처만 허용하고 외부 http(s)는 기본 브라우저로 보내며, **로컬 창의 새 창은 전면 거부한다**(`about:blank` 자식이 부모 webPreferences를 상속하기 때문 — preload 상속 차단). 미등록 webContents는 가장 제한적인 로컬 취급(fail-closed)이다. 부팅은 `userData` 지정 → 단일 인스턴스 잠금 순서로 고정한다(잠금 키가 userData에서 파생). **`spellcheck:false`**로 확정한다. 메뉴에는 명시 액셀러레이터·편집 role을 두지 않는다(role 기본 키 reload/zoom만 허용 — SPA 예약키와 교집합 0). 패키징은 패키저 없이 Electron 런타임 폴더 복사 + `resources/app` 화이트리스트 배치로 직접 조립한다(자동 업데이트·설치 관리자·코드 서명 없음). `electron`(43.4.0 정확 고정)은 **devDependency**이며 런타임 의존성 5개는 불변이다. 저장된 서버 출처가 `http:` + 비-loopback일 때는 **그 출처 하나만** secure context로 취급하는 Chromium 스위치(`unsafely-treat-insecure-origin-as-secure` + `enable-features` 병합)를 app ready **전** 1회 적용한다(2026-08-13 사용자 확정, phase 63 — 판정 단일 출처는 `client/lib/secureOrigin.js` 순수 모듈, loopback·https는 미적용, 콤마·와일드카드 값은 fail-closed). exe에는 아이콘(`packaging/icon/app.ico` — 순수 Node 생성기 커밋본, sha256 잠금)과 버전(1.0.0 → PE 1.0.0.0)·제품명 리소스를 `resedit`(devDependency, 네이티브 0)로 부여한다(서버 SEA exe에도 postject 주입 전 동일 적용 — phase 63).
**이유**: 접속형이라 DB·백엔드가 중복되지 않고 서버 1곳만 업그레이드하면 화면까지 전파된다(SPA의 API base가 빈 문자열 = 상대 경로라 서버 출처만 열면 REST·SSE·업로드가 전부 따라온다 — web/** 무수정으로 브라우저 접속 경로와 동작이 갈라지지 않는다). 원격 페이지를 여는 셸에서 preload·nodeIntegration을 주면 서버 침해가 곧 클라이언트 PC 침해가 된다 — 그래서 Node 권한은 원격 창에 0이다. 정책(URL 정규화·health 판정·창/내비게이션·설정 파싱)·메뉴·sender 검증을 순수 함수로 뽑아 Electron 없이 단위 테스트로 잠갔다(ADR-010의 "명시 주입 > 런타임 탐지"와 같은 축). `spellcheck:false`는 Chromium 맞춤법 검사의 사전 다운로드·서버측 제안 같은 앱 밖 통신을 만들지 않기 위함이다(ADR-008의 egress 0 규율·폐쇄망 배치) — 맞춤법 기능은 SPA 자체 메뉴가 제공한다. 메뉴 액셀러레이터를 두지 않는 것은 에디터 단축키(Ctrl+Y=(계속)삽입·Ctrl+A·Ctrl+D 등)를 메뉴가 렌더러보다 먼저 삼키기 때문이다. 패키저 없이 조립하는 이유는 필요한 것이 폴더 복사와 이름 변경뿐이고 설치 관리자·자동 업데이트를 만들지 않기로 했기 때문이다(@electron/packager는 기록된 실패 시에만 폴백 — 이번 조립은 폴백 불사용).
**트레이드오프**: 폴더가 크다(실측 347.4MB, 압축 약 138MB — Chromium 런타임 동봉). 서명이 없어 SmartScreen 경고가 뜬다. 자동 업데이트가 없다(셸 변경은 폴더 교체 운영 — 단, 화면 변경은 서버 재배포만으로 전파된다). 평문 HTTP LAN 접속의 클립보드 비활성(2026-08-13 실측: `127.0.0.1`은 정상, LAN IP는 `navigator.clipboard` undefined)은 secure-origin 스위치 채택으로 해소됐다(phase 63 통합 실측 2026-08-14: LAN IP에서 `isSecureContext` true·클립보드 실왕복 성공). 대신 **보안 트레이드오프**가 생긴다: 설정된 그 출처 하나에 한해 브라우저의 secure-context 제약이 완화되므로 **그 서버가 침해되면 secure context 전용 API 표면이 그 출처에 열린다** — 완화 범위는 출처 1개이고 값은 저장된 설정에서만 나오며, 근본 해결은 서버 HTTPS 종단이다(그때 스위치는 조건(http + 비-loopback)상 자동 비적용된다). 스위치는 부팅 1회 적용이라 최초 설정·주소 변경 후 재시작 1회가 필요하고(안내 다이얼로그·문서화), 브라우저 접속에는 이 완화가 없다. 인쇄는 Chromium 동작에 의존한다(시스템 인쇄 대화상자는 실기 육안 확인 미완 — 폴백은 메뉴에서 `webContents.print()`). 창을 정상적으로 닫으면 편집 잠금 해제 요청이 도달함을 실측했으나 강제 종료·크래시에서는 보장이 없다(복구는 데스크 강제 해제). 맞춤법 밑줄이 표시되지 않는다(spellcheck:false의 대가 — news.md 174행의 `spellcheck=true` DOM 설정이 셸에서 무효가 되는 **클라이언트 예외**이며, 2026-08-13 사용자 확정으로 **확정 예외**다 — 맞춤법은 SPA 자체 메뉴가 제공한다). 새로고침·확대/축소가 키가 아니라 메뉴 클릭이다(role 기본 키가 살아 있는지는 실기 확인 대기). Electron 버전이 배포물에 고정되어 보안 패치에 재빌드가 필요하다(ADR-010과 동형). 크로스 컴파일은 불가하다(빌드 머신 플랫폼 런타임을 복사한다). exe 리소스 메타(제품명·아이콘)는 phase 63이 `resedit`으로 부여해 Electron 기본값이 남지 않는다(아이콘 6항목·FileVersion 1.0.0.0 — @electron/packager 전환 없이 직접 조립 유지). 부작용으로 리소스 편집 시 Authenticode 서명이 제거되지만 이 프로젝트는 코드 서명을 하지 않아 손실이 없다.

### ADR-012: 서버는 데이터 폴더당 단일 인스턴스 — 전용 잠금 파일의 SQLite EXCLUSIVE 트랜잭션 (PID 파일·타이머 없음)
**결정**: 서버는 부팅 시 `<DATA_DIR>/instance-lock.db`에 전용 SQLite 연결(`busy_timeout=0`)을 열고 `BEGIN EXCLUSIVE` 트랜잭션을 **프로세스 수명 동안 유지**한다(커밋/롤백하지 않는다 — 해제는 OS가 프로세스 종료 시 수행). 그 파일에는 테이블·행을 만들지 않는다(0바이트 유지 — 잠금은 파일 내용이 아니라 열린 핸들에 있다). 획득 실패가 `SQLITE_BUSY`(확장 코드 포함 하위 8비트 5)면 = 같은 데이터 폴더를 쓰는 다른 인스턴스가 실행 중 → stderr에 원인·데이터 폴더 절대 경로·해결 2가지(기존 서버 종료 후 재시작 / `DATA_DIR` 분리)를 동기 출력하고 `exit 1`. **그 밖의 모든 실패**(잠금 파일 손상·열기 불가·잠금 모듈의 예상 밖 예외)는 경고 로그 1줄 후 **부팅을 계속한다**(잠금 없이 뜬다). 판정 위치는 `bootstrap`의 `dataDir` 보장 직후·`news.db` 열기 직전이며 dev(`npm run server`)·SEA exe 공통이다(packaged 여부 무관, `DATA_DIR` 기준). 구현은 `src/db/instanceLock.js`(잠금 유지 연결은 모듈 스코프 보관 — 참조가 끊기면 GC가 잠금을 조용히 푼다는 실측 함정 때문), 타이머·하트비트·재시도·시그널 핸들러는 두지 않는다(ADR-008). 클라이언트 Electron 셸의 `requestSingleInstanceLock`(ADR-011)과는 **별개 축**이다(대상·메커니즘·실패 모드가 다르다).
**이유**: 세션 스토어(ADR-004)·SSE EventEmitter(ADR-005)·배부 스풀 기록(ADR-008)이 전부 프로세스 로컬이라, 같은 `news.db`를 공유하는 두 인스턴스는 split-brain이 된다(한쪽 로그인 세션이 다른 쪽에서 무효, 실시간 신호 반쪽, 배부 중복 여지). phase 64의 부트 연결 `busy_timeout=5000`이 부팅 SQLITE_BUSY 즉사를 없애면서 이 공존이 더 쉬워졌다(실측: 같은 `DATA_DIR`·다른 `PORT` 두 인스턴스가 둘 다 health 200). OS 파일 락 방식이라 **크래시·강제 종료 후 잔류 락이 없다**(실측: SIGKILL 직후 5ms 내 재획득, 쓰레기 `-journal`도 자동 복구). PID 파일 방식(O_EXCL + stale 판정)은 크래시 후 파일이 영구 잔류하고 Windows PID가 빠르게 재사용되며 `data\` 백업 복구로 남의 PID가 되살아나 — 죽은 인스턴스의 PID를 무관한 산 프로세스가 물면 **운영자가 서버를 못 올린다**(오탐 = 최악 실패 모드)는 이유로 기각했다. `news.db` 자체 EXCLUSIVE는 자기 부트 연결이 막혀 자멸이라 기각. 경로 문자열 비교가 아니라 파일 핸들로 판정하므로 심볼릭 링크·UNC/매핑 드라이브·대소문자 표기 차이가 같은 잠금으로 수렴한다. 잠금 연결의 `busy_timeout=0`은 충돌 판정 실측 38ms vs 5000일 때 7,563ms — 두 번째 인스턴스는 즉시 죽어야 한다.
**트레이드오프**: 같은 데이터 폴더로 의도적 다중 기동이 불가능해진다(필요하면 `DATA_DIR` 분리 — 다중 인스턴스 지원은 ADR-004에 기록된 별도 과제다). `data\`에 파일 1개(+ 잠금 유지 중 `-journal`)가 늘지만 0바이트 표식이라 백업·복구에 영향이 없다(백업 사본이 되살아나도 무해). 잠금 파일을 열 수 없거나 손상된 드문 경우 잠금 없이 부팅한다(경고 1줄) — 부팅 차단 오탐보다 낫다는 선택이며, 그때는 이 결정 이전과 같은 무보호 상태다. 잠금 파일이 읽기 전용이면 EXCLUSIVE가 성립하지 않아 조용한 무보호(미탐)가 될 수 있다 — 단, 그 상태는 news.db 쓰기도 막혀 실운영이 성립하기 어렵다(오탐이 아닌 미탐 방향). 파일시스템 락에 의존하므로 `data\`를 **SMB/네트워크 드라이브**에 두는 배치는 검증 범위 밖이다 — **두 방향 모두 미검증**: ① 잠금이 동작하지 않아 두 인스턴스가 공존할 수 있고 ② 반대로 락 잔류로 정상 재기동이 막힐 수도 있다(네트워크 파일시스템의 락 잔류는 알려진 현상 — "오탐은 안 난다"고 단정할 수 없다). 권장 배치는 로컬 디스크이며, 네트워크 배치에서 재기동이 막히면 복구는 "모든 인스턴스 종료 확인 → 서버 중지 상태에서 잔여 잠금 파일 제거 → 재기동"이다. EXCLUSIVE 유지 중에는 다른 프로세스가 그 파일을 읽을 수 없어 잠금 보유자 메타(PID·포트)를 표시할 수 없다 — 콘솔 메시지는 PID 없이 행동 지시만 한다(낡은 PID 안내는 무관한 프로세스를 죽이라는 지시가 된다).

### ADR-013: Spring 포팅 서버는 `server-spring/` 독립 모듈 — starter-security·Spring Session 미채택, DDL 0, 자체 필터 체인, 패리티는 계약 스위트가 판정
**결정**: C++/Spring 포팅 계획서 P1의 Spring 서버는 리포 루트 하위 **독립 Maven 모듈 `server-spring/`**로 둔다(`harness:server-spring:0.0.1-SNAPSHOT` · base package `harness.news` · Java 21 · Spring Boot 4.1.0 · 계층 `controller → service → repository → db` · 생성자 주입만). Node 서버(`server/**`·`src/**`)는 **무수정**이고 두 서버가 공존한다. 네 가지를 명시적으로 결정한다. ① **`spring-boot-starter-security`·Spring Session을 쓰지 않는다** — 세션 토큰(64-hex 랜덤·권한 미포함·1시간 슬라이딩·같은 userId 재로그인 시 기존 세션 전부 무효화 — ADR-004)과 `sid` 쿠키 2변형(dev `Lax` · prod `Secure`+`SameSite=None`)·`x-session-id` 헤더 폴백·에러 shape(`{ok:false,reason:...}`)이 이미 계약으로 동결돼 있어 프레임워크 기본값(전 라우트 기본 잠금·기본 401/403 페이지·`JSESSIONID`)과 충돌한다. bcrypt만 `spring-security-crypto`에서 가져오되 대조는 `BCrypt.checkpw`를 **직접** 부른다(실측: spring-security 7.1의 `BCryptPasswordEncoder.matches("", hash)`는 해시가 맞아도 `false` — 상위 검증기가 빈 raw 비밀번호를 탈락시킨다. bcryptjs **이유**: 이 포팅의 합격 기준은 "기능이 된다"가 아니라 **와이어 바이트가 같다**이다(리포트 diff는 상태코드 정수와 헤더 문자열을 정확 비교한다). 프레임워크 기본값은 그 기준에서 대부분 어긋난다 — Spring MVC의 JSON 응답에는 charset 파라미터가 없고, 서블릿 API로 Content-Type을 지정하면 컨테이너가 `application/json;charset=UTF-8`로 **재조립**해 세미콜론 뒤 공백 1바이트가 사라지며, `ResponseCookie.toString()`의 속성 순서도 express `res.cookie`와 다르다. 그래서 와이어 포맷 정규화를 **한 클래스**(coyote 응답에 완성된 문자열을 직접 기록)로 모으고 필터를 직접 썼다. 보안 축을 프레임워크에 위임하지 않은 이유도 같다: starter-security를 넣는 순간 401/403의 shape과 필터 순서가 프레임워크 소유가 되어 계약이 프레임워크 업그레이드에 인질로 잡힌다. DDL을 금지한 이유는 운영 DB 안전이다 — 스키마를 두 서버가 각자 만들면 P3 전환기에 어느 쪽이 정본인지 사라지고, 조용한 `ALTER`는 되돌릴 수 없다. 마지막으로 판정을 계약 스위트에 맡긴 것은 **사람의 눈으로 패리티를 판정하지 않기 위해서**다(기능 테스트는 상태코드 204/200 차이와 Content-Type 공백을 통과시킨다 — 실제로 그 변이가 기능 green·패리티 red로 잡혔다).
**트레이드오프**: 프레임워크 기본값을 포기한 대가로 **직접 구현한 와이어 포맷·필터 순서를 계속 지켜야 한다**(에러 shape·쿠키 직렬화·CORS 허용 헤더 4종·필터 순서는 전부 테스트로만 고정돼 있고, 새 필터를 잘못된 순서에 끼우면 계약이 조용히 깨진다). Content-Type 바이트 seam은 **Tomcat(coyote) 전용**이라 컨테이너를 바꾸면 첫 JSON 응답이 500으로 죽는다(조용한 폴백 대신 시끄러운 실패를 택한 결과다). 프레임워크가 만드는 응답 중 이 서버가 가로채지 않는 것(405·415의 Boot 기본 `/error` JSON)은 다른 에러와 shape이 다르다. **helmet 등가 보안 헤더(CSP·X-Content-Type-Options·HSTS)와 HTTPS 강제가 아직 없다** — 계약이 그 축을 동결하지 않아 게이트가 전부 green이어도 공백은 실재하며, P3 운영 전환 전에 반드시 채워야 한다(누가 소유하고 계약을 늘릴지는 미결). 세션이 프로세스 로컬이라 다중 인스턴스로 가면 단일 세션 정책·즉시 무효화의 구현이 달라진다. 커넥션 풀 1은 SQLite 단일 파일과 Node 단일 연결에 맞춘 것이라 동시성 한계가 그대로 남고, 두 서버가 **같은 `news.db`를 동시에** 여는 상황은 전혀 검증되지 않았다(하네스는 프로파일마다 DB를 분리한다). 계약이 시계를 주입할 수 없어 세션 1시간 만료·다이제스트 24h 창 같은 시간축은 계약이 아니라 **Java 단위 테스트**가 소유한다. Java 빌드는 npm 파이프라인 밖이라(`npm test`·`lint`·`build`는 이 모듈을 보지 않는다) 별도 커맨드와 `JAVA_HOME` 지정이 필요하고, 상시 CI 게이트는 아직 없다.
